## Files created

- **`server/queue/redisClient.ts`** — singleton `ioredis` connection configured for BullMQ (`maxRetriesPerRequest: null`, `enableReadyCheck: false`, exponential reconnect backoff capped at 10s, `reconnectOnError` for READONLY during ElastiCache failover). Throws at module load if `REDIS_URL` is unset (fail-fast). Exports `redisConnection` and `isRedisHealthy()`.
- **`server/queue/bullmq.ts`** — `createQueue<T>(name, opts?)` and `createWorker<T,R>(name, processor, opts?)` factories bound to the shared `redisConnection`. Default concurrency 5; default job options `{ attempts: 3, backoff: { type: "exponential", delay: 1_000 } }`. TODO marker for Phase 8 queue registration.

## Environment variables

- **`REDIS_URL` (required).** Validated by `validateEnv.ts` in `ENV_VARS`. Use `rediss://` (two s's) to enable TLS — AWS ElastiCache in-transit encryption requires it.

## Startup health-check behaviour

On each boot of `server/_core/index.ts`:

1. `isRedisHealthy()` runs a `PING` against the singleton connection.
2. Success logs `Redis connection established` at INFO.
3. Failure logs `Redis connection failed …` at ERROR and **startup continues**. No Phase 1 runtime path depends on Redis, so a transient ElastiCache outage must not prevent the app from booting. The existing `/health` endpoint already reports Redis status separately via `tokenBlocklist.isBlocklistHealthy()` — that path is unchanged.
4. `TODO(Phase 8)`: when async agent tools land, this check becomes fail-fast (`process.exit(1)` on failure).
